# Elicit requirements

Read the intake, intent, project overlay, and applicable local policy. Preserve
traceability to the intent and distinguish requirements from design choices.

Capture user scenarios, functional and quality requirements, failure and boundary
behaviour, data needs, dependencies, acceptance scenarios, assumptions, and open
questions. Apply project-specific accessibility, privacy, security, compatibility,
and operational requirements when relevant.

Use clear identifiers and observable language. Mark consequential ambiguity instead
of silently selecting an answer. Do not add technical architecture unless it is an
explicit constraint.

Use `templates/requirements.yaml` or the adopting project's compatible template.
Do not treat draft requirements as approved.
